# Project map

A project map is a set of linked Markdown files in `.swarmup/map/` that say what each part of a
project is for: its modules and flows for code, its pages and content sources for a website, or
its campaigns, audiences and channels for marketing work. A run reads the one or two nodes it
needs instead of reading the whole project, and agents keep the nodes true as part of each
change. `swarmup map check` finds what a change left out, with no model.

The map is opt-in per project: a folder without `.swarmup/map/` gets no checks and no prompt
block. This repo has one; `swarmup map` in a checkout lists its nodes.

## Where it lives

`.swarmup/map/` at the top of the folder the work happens in: the code checkout for a code
project, or the task store's folder for a project that has no code repo.

```text
.swarmup/map/
  index.md          # the root node (kind: root): what the project is, links to the top areas
  core/index.md     # a folder node, id `core`
  core/fold.md      # a node, id `core/fold`
  kinds.yml         # optional: more kinds
  ignore            # changed paths that need no node, one glob per line
  README.md         # the format, for people who open the folder
  _INDEX.md         # generated by `swarmup map index`; never edit it
```

A node is `<name>.md` or `<name>/index.md`; its id is the path without `.md` or `/index`. The
generated list is `_INDEX.md`, not `INDEX.md`: on Windows and macOS that name is the same file as
the root node `index.md`.

## Node format

```markdown
---
kind: module
summary: Folds a task's events in ULID order into its state
covers:
  - packages/core/src/fold.ts
  - packages/core/src/plan.ts#effective-plan
links: [store, /docs]
verified: 25fbe7b8
---

# Fold

Purpose, how it works, invariants, entry points, gotchas.
```

| Field          | Required                | Meaning                                                                                                                                    |
| -------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `kind`         | yes                     | What the node describes; see [Kinds](#kinds).                                                                                              |
| `summary`      | yes                     | One line, at most 120 characters. It is what `_INDEX.md`, search and run prompts show.                                                     |
| `covers`       | no                      | Paths or globs from the project top, or `http(s)` URLs. A folder covers everything in it; an `#anchor` suffix is allowed and ignored.      |
| `links`        | no                      | Node ids, relative to the node's folder first, then to the map top. A link that starts with `/` is from the map top only; `/` is the root. |
| `verified`     | no                      | The commit the node was last checked against.                                                                                              |
| `review_after` | when `covers` has a URL | A date (`2026-12-01`) after which the node needs a fresh look, since a URL can change without a diff.                                      |

The body holds purpose, how it works, invariants, entry points and gotchas: at most 60 lines, and
at most 40 for the root. Split a longer node into linked ones.

In `covers`, `*` and `?` stay inside one path segment and `**` crosses folders; either path
separator works. `ignore` uses gitignore-like globs: a pattern without a `/` inside matches a
name in any folder (`dist/`, `*.log`), a leading `/` anchors it at the top, and `!` takes paths
out again. Built in: the map and the task store (`.swarmup/`), `node_modules/`, `dist/`,
`build/`, `out/`, `coverage/` and lockfiles.

## Kinds

| Project type     | Kinds                                                                       |
| ---------------- | --------------------------------------------------------------------------- |
| code             | `module`, `service`, `entry`, `data`, `flow`                                |
| website          | `page`, `section`, `component`, `content-source`                            |
| campaign/content | `campaign`, `audience`, `message`, `channel`, `asset`, `calendar`, `metric` |
| any              | `root`, `goal` (outcome, done, next, open questions, decisions), `area`     |

Every kind is valid in every project. `kinds.yml` adds more, as a list (`- press`) or a map from
name to what it is for (`press: coverage in the media`).

## Commands

```sh
swarmup map parser crash          # nodes that match any word, best first (top 10)
swarmup map                       # every node, one line each
swarmup map --file src/fold.ts    # the nodes that cover a file
swarmup map show core/fold        # the node, plus one line per link and per node linking to it
swarmup map index                 # regenerate _INDEX.md
swarmup map check [--base REF]    # check the map against the change; --json for scripts
swarmup map init [--type code|website|campaign]   # start a map: root node, ignore, README
```

Each takes `--cwd DIR`. `swarmup map init` writes no content: it detects the type from the
repo survey `swarmup adopt` uses (a site framework or mostly pages is a website, a manifest or
source files is code, otherwise a campaign) and leaves the root summary for you to write.

## The check

`swarmup map check` compares the working tree with where HEAD left its base: `--base`, else the
remote's default branch, `main` or `master`. Committed and uncommitted changes count, and so do
untracked files.

Errors (exit 1):

- A changed path that no node covers and `ignore` does not list. Deleted paths need no node.
- A `covers` entry that matches no file.
- A link to a node that does not exist.
- A summary over 120 characters, or a body over 60 lines (40 for the root).
- A node that covers a URL and has no `review_after`.
- Missing frontmatter fields, an unknown kind, or no root node.
- `_INDEX.md` missing or different from what `swarmup map index` writes (line endings and
  trailing spaces aside).

Warnings (exit 0), for the reviewer:

- A node whose covered files changed while the node file did not: is it still true?
- A node past its `review_after` date.

## In runs and merges

When the run's checkout (or the code checkout of the task's root) has a map, swarmupd adds a
short block to a task run's prompt: the root's summary and up to 5 nodes that cover the task's
files or share words with its title and description. A work run is told to read nodes on
demand, update or add nodes in the same commit when its change affects them, and run
`swarmup map index` and `swarmup map check` before it asks for review. A review run is asked
whether the change made any node wrong, with the check's warnings for the reviewed commit,
computed against the base's map. See [The project map in the
prompt](supervisor.md#the-project-map-in-the-prompt).

To make the check a merge gate, add it to the root's merge `checks`; see
[Merging approved work](supervisor.md#merging-approved-work).

## Keeping it in shape

A weekly repeat keeps the map tidy. In the project's root:

```sh
swarmup repeat add map-gardening --title "Garden the project map ({date})" \
  --start "2026-11-23 09:00" --every weekly --owner claude:docs --type task \
  -m "Run \`swarmup map check\`. Split nodes over the size limits into linked nodes, refresh \`review_after\` on URL nodes you checked, link or remove orphan nodes no other node links to, fix covers that match nothing, then run \`swarmup map index\` and ask for review."
```
